# Бенчмарк трёх движков — этап 7, 2026-10-28

## Запуск

```powershell
.\scripts\build_benchmarks.ps1
python benchmark/prepare_datasets.py
python tests/test_benchmark.py
python benchmark/run_benchmark.py --runs 10 --output results/stage7-new
python benchmark/audit_results.py results/stage7-new --freeze-sources
```

Если `data/benchmark-stage7` уже создан, повторно запускать prepare не нужно:
runner использует `data/benchmark-stage7/datasets.json`. Для нового набора
prepare принимает путь нового каталога; runner — `--manifest path/datasets.json`.
Существующие результаты/наборы не перезаписываются.

Фактические результаты находятся в `results/stage7-20261028/`:
`results.csv`, `environment.json`, `raw_runs.json`, `latencies/*.json.gz`,
`benchmark_summary.md`, `audit.json` и `source_snapshot/`.
Сводка для репозитория: [benchmark-stage7-audit.json](benchmark-stage7-audit.json).
Live-проверка: [live-stage7.json](live-stage7.json).

## Согласование сборок

- CPU: 12th Gen Intel Core i7-12650H, Windows x64.
- Clang 23.1.4 для обоих C++ engines и сгенерированного Goose C/runtime.
- C++: отдельный CMake preset `clang-benchmark`, `-O2 -DNDEBUG`.
- Goose v2026.3: `-O2`, native Clang `-O2`, без GS_DEBUG.
- Проверки входных событий и обязательные проверки языка сохранены.
- Одинаковые исходные events.bin для всех движков, SHA-256 фиксируются.

Вспомогательный C-модуль `src/common/measurement.c` общий для всех:
только QPC и Peak Working Set. Парсинга, checksum, JSON и ядра стакана в нём нет.
Goose kernel/reader остаются самостоятельными. Маленький включаемый header
проверяет Release-флаги непосредственно в сгенерированном Goose C;
Debug-программа отказывается от измерений. Проверка не полагается на флаги
отдельно кэшируемого native helper.

## Границы измерений

### Core

Вход заранее прочитан, проверен и декодирован; книга создана до таймера.
Таймер охватывает один проход apply по всем событиям. Включены валидация
каждого события, изменения уровней, snapshot/reset и сохранение архива.
Checksum и JSON считаются после остановки таймера. Подготовка, уничтожение
книги и file I/O исключены. Каждый процесс получает свежую книгу: искусственных
сбросов monotonic clock внутри рабочей книги нет.

### Offline

Таймер запускается перед чтением файла, включает чтение, CRC/проверку формата,
декодирование, создание книги и применение событий. Он останавливается до
расчёта checksum/JSON и уничтожения книги. Это локальный pipeline с прогретым
OS file cache после warmup, а не замер холодного диска.

И для core, и для offline один прогон — один проход файла, без повторений
последовательности внутри процесса. CSV events включает reset: 10002 для
реального набора, 100100 для синтетического; market_events хранится отдельно.

### Задержки

Throughput измеряется в процессе без часов на каждое событие. Для core
отдельный instrumented процесс вызывает тот же общий QPC до и после apply,
сохраняет все разности и 10000 пустых пар вызовов часов для калибровки.
Перцентили: nearest rank, `ceil(q*N)` с индексацией от 1, по каждому прогону.
В сводках приводятся медианы перцентилей десяти прогонов, не перцентиль
распределения времён запусков и не перцентиль средних ns/event.

Накладные расходы часов не вычитаются: вычитание квантиля калибровки из
квантиля измерений не даёт корректного квантиля времени ядра.
Raw latency samples и timer samples сохранены полностью в gzip JSON.

Offline p50/p99/p99.9 намеренно пустые: reader загружает файл целиком, поэтому
перцентили apply нельзя выдавать за задержки полного pipeline для каждого
события. Offline показывает время всей цепочки и throughput/RAM.

### Память

`peak_memory_mb = PeakWorkingSetSize / 1000000`, пиковый физический working set
всего процесса. Значение берётся из неинструментированного throughput-процесса,
до построения JSON. Это включает загрузку и подготовку, не только данные книги,
и не является reserved virtual address space стеков Goose. В итоговой таблице
показан максимум десяти пиков, не усреднённый максимум.

## Контроль эксперимента

Два раздельно помеченных набора: реальная запись Bybit (10000 рыночных событий)
и искусственная stress-последовательность (99900 рыночных + 200 reset).
По одному прогреву на сочетание dataset/mode/engine, затем по 10 измерений.
Порядок движков вращается и разворачивается, порядок core/offline чередуется.

Перед измерениями три полных replay должны дать одинаковые состояния,
архивы и checksum истории. Каждый измерительный процесс возвращает текущую
и last_valid checksum, и runner проверяет обе. Проверять только пустую книгу
после последнего reset было бы недостаточно.

Всего 120 throughput-прогонов и 60 latency-проходов. Audit заново проверил
все 120 CSV строк по raw native JSON, 3303060 latency samples, расчёт квантилей,
калибровку, SHA-256 данных/бинарников и сохранённые копии исходников.
Environment содержит реальные команды компиляции и Goose build log.
Git commit отсутствует: записаны null и dirty=true; идентификатор не выдуман.

Привязка к ядру и power policy не менялись; фоновые приложения не контролировались.
Это проверяемые локальные результаты данного набора/реализаций, не универсальное
утверждение о превосходстве языка.

## Измеренный результат

Реальный набор; throughput — медиана прогонов, latency — медиана перцентилей
отдельных instrumented проходов, RAM — наибольший peak из десяти прогонов.

| Engine | Core events/sec | p50, мкс | p99, мкс | p99.9, мкс | Peak MB |
|---|---:|---:|---:|---:|---:|
| C++ map | 1981440 | 0.30 | 3.75 | 8.95 | 8.643 |
| C++ vector | 2389914 | 0.30 | 2.90 | 6.20 | 8.630 |
| Goose | 3831108 | 0.20 | 1.80 | 4.25 | 7.664 |

Главное сравнение Goose с оптимизированным C++ vector:
core throughput 1.603x (около +60.3%); отношение медиан p99 соответствует
снижению на 37.9% в инструментированном эксперименте.
Offline throughput: C++ vector 1076819 events/sec, Goose 1381321 events/sec,
отношение 1.283x. Core и offline ускорения не взаимозаменяемы.

На реальном core диапазон throughput по десяти прогонам:
map 1.887–2.038 млн/с, vector 2.280–2.511 млн/с, Goose 3.533–3.920 млн/с.

Синтетический core: map 14.090 млн/с, vector 19.676 млн/с, Goose 36.215 млн/с.
Синтетический offline: map 2.698 млн/с, vector 2.840 млн/с, Goose 3.438 млн/с.
Синтетика не заменяет реальный поток и показана отдельно.

### Предел точности таймера

QPC = 10 МГц: квант 100 нс = 0.1 мкс. Калибровка: медиана пустой пары
вызовов 0 нс, p99 100 нс. Ноль здесь означает попадание обеих отметок в один
квант, а не отсутствие накладных расходов.

Синтетический Goose p50 в raw CSV равен 0: операции попали ниже кванта часов.
Это **не нулевое время обработки**. Синтетические p50 всех движков находятся
на уровне разрешения часов или ниже; сравнивать их как точные sub-100-ns
задержки нельзя. Для столь коротких операций основным результатом остаётся
batch throughput. Значения raw CSV не исправлялись и не подменялись.
