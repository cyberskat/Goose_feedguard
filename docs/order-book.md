# Стакан std::map — этап 4

```powershell
$env:PATH = 'C:\msys64\clang64\bin;' + $env:PATH
.\build\clang-release\book_cpp.exe --input data/normalized/events.bin
```

Программа проверяет бинарный файл и события, выполняет replay, выводит один
JSON-объект на stdout. Ошибки идут на stderr с ненулевым кодом выхода.
Без аргументов и с `--help` выводится справка без запуска replay.
Бенчмарк и численные заявления об ускорении на этом этапе отсутствуют.

Сохранённый результат реального replay: [book-stage4.json](book-stage4.json).
Независимая проверка этого результата по первоначальному JSONL:

```powershell
python scripts/verify_book.py docs/book-stage4.json data/raw/btcusdt-20261027-linear-x25519.jsonl data/metadata/btcusdt-linear-20261027.json
```

Python использует Decimal, словари и собственную реализацию FNV; он не вызывает
C++ reader или engine и не восстанавливает стакан из результатов C++.

## Семантика и ошибки

`MapBook` хранит BID в std::map с убывающим порядком, ASK — с возрастающим.
Snapshot полностью заменяет обе стороны. Delta вставляет новый уровень,
меняет существующий объём или удаляет уровень при quantity=0. Удаление
несуществующей цены ничего не меняет. Перестановка независимых изменений
внутри delta не влияет на отсортированный результат.

Первый snapshot может инициализировать новую пустую книгу напрямую. После
инициализации переход к другому session требует явного reset. После reset
delta запрещены до нового snapshot. `u=1` разрешён только для snapshot;
`seq` не обязан увеличиваться на 1. Дополнительных предположений о шаге u/seq
нет. Steady timestamp не уменьшается, в том числе после reset.

Проверки до изменения состояния: тип события, session, timestamp, количества
изменений, положительные цены, неотрицательные объёмы, шаги инструмента,
дубликаты цены на одной стороне, сортировка и максимальная глубина snapshot.
Обе стороны проверяются до применения первой из них.

Для snapshot сначала строятся две временные карты, затем выполняется swap.
Для delta сначала выделяются все новые узлы обеих сторон. Затем существующие
уровни изменяются/удаляются, а подготовленные узлы переносятся через map::merge.
Числовые компараторы не бросают исключений, std::allocator у карт одинаковый;
при переносе узлов новые аллокации не нужны. Полного копирования стакана на
каждую delta нет. Scratch-массив для поиска дубликатов переиспользуется.

Reset сначала сохраняет достоверное состояние, затем очищает текущие уровни
и выставляет valid=false. Повторный reset недостоверной книги не перезаписывает
архив пустым состоянием. После reset best_bid, best_ask и spread возвращают null.
Если одна сторона пуста, spread также null. Spread — точная разница ASK-BID
в целых единицах цены; для допустимых положительных int64 цен она не переполняется.

Карты не обрезаются молча до 50 уровней: delta применяется целиком.
В реальном проверенном потоке сохранялись 50 уровней с каждой стороны.
Пересечённый вход не исправляется автоматически: возвращается фактический spread,
включая отрицательный. Фильтрация такого потока требует отдельной политики.

## Поля результата

- `mode=verify_replay`, `engine=cpp_map`.
- `events`, `market_events`, `resets` — числа обработанных событий.
- `current` — текущее состояние, valid, session, u, seq, BID/ASK, лучшие уровни,
  spread и checksum.
- `last_valid_before_reset` — последнее достоверное состояние перед reset либо null.
  Оно может относиться к предыдущей сессии; session сохраняется в объекте.
- `checksum` — checksum текущего состояния.
- `history_checksum` — checksum всей последовательности состояний после событий.

Checksum — строки из 16 строчных hex-цифр, чтобы не терять точность uint64
в JSON-клиентах. Цены/объёмы остаются JSON integer; потребителю нужен parser
с точной поддержкой int64. Масштабы указаны в price_decimals/quantity_decimals.

## Каноническая checksum состояния

FNV-1a-64: offset basis `14695981039346656037`, prime `1099511628211`.
Для каждого байта: `hash = (hash XOR byte) * prime modulo 2^64`.
Вычисление использует uint64, без signed overflow.

Байты в точном порядке:

1. Восемь ASCII байт `BFGBOOK1`.
2. price_decimals u32 LE, quantity_decimals u32 LE.
3. tick_size i64 LE, quantity_step i64 LE.
4. valid u8: 0/1.
5. session u64 LE, u u64 LE, seq u64 LE.
6. BID count u64 LE, ASK count u64 LE.
7. BID по убыванию цены, затем ASK по возрастанию: пары price i64 LE, quantity i64 LE.

Заголовок состояния занимает 73 байта. Время получения и SHA-256 полного REST
ответа в checksum не включаются; они не являются состоянием стакана.
Параметры масштаба и шаги включены. FNV предназначен для проверки согласованности
реализаций, не для защиты от намеренных коллизий.

История: FNV начинается с девяти ASCII байт `BFGTRACE1`. После каждого
успешно применённого события добавляются kind u8, session u64 LE, u u64 LE,
seq u64 LE и checksum текущего состояния u64 LE. Никаких разделителей/padding нет.
Так обнаруживаются промежуточные ошибки, даже если финальный reset очищает книгу.

В текущем режиме verification checksum вычисляется после каждого события.
Эта проверка не должна входить в будущий замер чистой производительности apply.

## Результат проверки 2026-10-27

- GCC и Clang, Debug и Release: по 28/28 автоматических тестов.
- Все четыре сборки выдали одинаковый JSON для 10002 событий
  (10000 рыночных + 2 reset).
- Текущая книга после финального reset: valid=false, пустые BID/ASK;
  checksum `e898d48c8118d4d9`.
- History checksum: `133ad3f85b1d7b87`.
- Последнее достоверное состояние: 50 BID, 50 ASK;
  checksum `a8bea05ec3dc51c7`, u=42927073, seq=833683244427.
- Лучший BID `[806082,8075]`, ASK `[806083,871]`, spread=1 целая единица цены.
  При масштабах 10/1000 это исторические цены 80608.2/80608.3 и spread 0.1.
- Независимый Python replay подтвердил все уровни и обе итоговые checksum.
- В стресс-тесте 100000 событий каждое состояние и архив перед reset
  сравниваются с независимой моделью на vector, включая вставки, изменения,
  удаления, повторные snapshot и 100 сессий.
- Эталонные состояния вручную рассчитаны в test_book.cpp; независимые FNV
  значения сохранены в tests/fixtures/book-golden.json. Проверяется каждый шаг.
- Ошибочные события проверяются на сохранение уровней, метаданных, checksum,
  уже заполненного архива и возможности продолжить работу с корректным временем.

Численные показатели throughput/latency здесь не измерялись.
